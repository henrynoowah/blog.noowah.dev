봇 트래픽에 대응할 때 “차단”은 가장 눈에 잘 보이는 선택지다. 하지만 글로벌 서비스에서
IP나 국가를 넓게 막는 방식은 정상 사용자와 검색 크롤러까지 함께 잃을 위험이 있다.
이번 WAF 대응에서는 Azure Front Door WAF를 이용해 **봇으로 보이는 모든 요청**이
아니라, **여러 의심 신호가 겹치는 요청**만 JavaScript Challenge로 전환하는 데 집중했다.

이 글은 내부 정책값, 서비스 주소, 규칙 ID, 실제 지문 값은 공개하지 않는다. 대신 어떤
관측을 근거로 WAF 정책을 설계했고, 어떻게 오탐과 방어 효과를 함께 검증했는지 정리한다.

## 출발점이 된 글: 분석 화면 밖의 트래픽

이번 대응의 문제를 정리하는 데에는 GeekNews의
[「150만 페이지 웹사이트에서 scraper와 싸운 1년」](https://news.hada.io/topic?id=32244)이
많은 도움이 됐다. 그 글은 대규모 스크래핑이 단순히 비용 문제만이 아니라 분석 지표를
오염시키고, 실제 서비스 상태를 판단하기 어렵게 만든다는 점을 잘 보여준다.

특히 다음 네 가지 관점이 WAF 대응의 기준이 됐다.

1. **클라이언트 분석 도구가 아닌 서버·엣지 로그를 기준으로 본다.** JavaScript를 실행한
   방문자만 집계하는 분석 도구는 자동화 요청의 대부분을 놓칠 수 있다.
2. **IP 하나만으로 공격자를 식별하지 않는다.** residential proxy나 브라우저 자동화는
   IP를 빠르게 바꾸므로 IP별 rate limit만으로는 분산 요청을 잡기 어렵다.
3. **사람이 섞일 수 있는 범위에서는 block보다 challenge를 우선한다.** 정상 브라우저의
   이용 흐름을 최대한 유지하면서 자동화를 걸러낼 수 있다.
4. **Challenge solve rate를 오탐 지표로 쓴다.** 챌린지를 너무 많이 통과한다면 규칙은
   정상 사용자를 가로막고 있을 수 있고, 반대로 통과율이 매우 낮다면 표적의 자동화
   가능성을 더 강하게 뒷받침한다.

참조 글의 WAF는 다른 제품을 사용하지만, “관측 → 좁은 범위의 challenge → solve rate와
정상 사용자 지표로 검증”이라는 운영 원칙은 Azure WAF에서도 그대로 적용할 수 있었다.

## WAF 규칙을 조정하기 전에: 로그의 잡음을 먼저 줄였다

WAF를 조정하기 전에 애플리케이션이 만든 잘못된 자산 요청과, 준비되지 않은 런타임 설정에서
비롯된 잘못된 API 요청을 먼저 고쳤다. 이 변경으로 자체 유발 오류 요청은
90% 이상 줄었다.

이 작업이 중요한 이유는 WAF 규칙의 품질을 판단할 수 있게 만들기 때문이다. 애플리케이션이
계속 잘못된 요청을 만들면 WAF 로그에는 공격과 제품 버그가 섞인다. 그러면 좋은 규칙은
너무 넓게 설계되고, 나쁜 규칙은 정상 사용자에게 과도한 부담을 준다.

## 전후 지표: 절대값 대신 변화율로 보기

회사 서비스의 상세 운영 수치는 공개하지 않기 위해, 아래 표는 조치 전 값을 `100`으로 둔
상대 지표다. 코드 수정의 효과와 WAF 적용 이후의 트래픽 흐름 변화를 구분해 확인했다.

| 지표 | 조치 전 | 조치 후 | 해석 |
| --- | ---: | ---: | --- |
| 자체 유발 오류 요청 | 100 | 10 미만 | 잘못된 URL과 준비 전 설정 요청을 제거해 90% 이상 감소 |
| 오리진 도달 요청 | 100 | 약 65 | 불필요 요청 제거와 엣지 방어로 오리진 부하 감소 |
| 의심 자동화의 콘텐츠 도달 | 다수 요청이 콘텐츠 경로로 진행 | 대부분 Challenge에서 검증 | 콘텐츠 응답 전에 자동화 요청을 분리 |
| JS Challenge 결과 | 측정 대상 없음 | 발급 대비 통과·유효 비율이 낮게 유지 | 표적 트래픽이 자동화일 가능성을 뒷받침 |
| 정상 사용자 4xx 비율 | 기준선 | 유의미한 상승 없음 | 규칙이 정상 사용자에게 과도한 부담을 주지 않는지 확인 |

이 표에서 중요한 것은 “차단 수가 얼마나 늘었는가”가 아니다. 잘못된 요청이 먼저 줄었는지,
의심 트래픽이 실제 콘텐츠 대신 Challenge로 이동했는지, 그리고 정상 사용자 지표가 유지됐는지를
같이 보는 것이 핵심이다.

WAF 규칙 조정의 첫 단계는 새 규칙을 만들기보다, 다음 정보를 같은 시간대 기준으로 묶어 보는
일이었다.

- Azure Front Door 액세스 로그의 경로, 응답 코드, 캐시 상태, 원본 도달 여부
- WAF 로그의 규칙 유형, 매칭 조건, 액션
- Bot Manager의 관리형 봇 분류
- 사용자 에이전트와 JA4/TLS 클라이언트 지문
- 정상 사용자군의 성공 응답률과 4xx 비율

이렇게 보면 “한 IP가 너무 많이 요청했다”보다 훨씬 유용한 질문을 할 수 있다. 예를 들어
매 요청마다 IP가 바뀌더라도, 비슷한 비브라우저 지문과 봇 분류, 비정상적인 요청 패턴이
동시에 나타나는지 확인할 수 있다.

## 정책은 한 번에 차단하지 않고 단계적으로 설계했다

Azure Front Door WAF의 Bot Manager는 좋은 봇, 나쁜 봇, 알 수 없는 봇을 관리형 규칙으로
분류한다. 그러나 `Unknown`이 곧바로 “차단해야 하는 봇”을 의미하지는 않는다. 새 크롤러,
내부 연동, 사용자가 사용하는 특수 브라우저가 섞일 수 있기 때문이다.

그래서 정책을 다음 순서로 분리했다.

1. **확신이 있는 악성 신호**는 가장 높은 우선순위에서 차단한다. 일시적인 긴급 차단도
   여기에만 둔다.
2. **검증된 크롤러**와 서비스 운영에 필요한 트래픽은 명시적으로 허용한다. 이 예외는
   사후 추가가 아니라 정책 설계의 시작점이어야 한다.
3. **알 수 없는 봇 분류**는 우선 로그로 관찰한다. 충분한 표본을 모은 뒤, 반복적으로
   의심스러운 신호와 겹치는 범위만 JS Challenge로 바꾼다.
4. **JA4/TLS 클라이언트 지문**은 보조 신호로 사용한다. 일반 브라우저와 공유되는 넓은
   지문은 대상에서 제외하고, 비브라우저 특성이 분명한 좁은 지문만 후보로 삼는다.

아래는 실제 배포 파일이 아닌, 이 우선순위를 설명하기 위한 의사 설정이다.

```yaml
rules:
  - name: block-confirmed-abuse
    match: confirmed-abuse-signal
    action: Block

  - name: allow-verified-crawlers
    match: verified-crawler
    action: Allow

  - name: challenge-overlapping-bot-signals
    match:
      bot-classification: unknown-or-suspicious
      client-fingerprint: non-browser-pattern
    action: JSChallenge
```

중요한 점은 `Unknown`만으로 챌린지하지 않았다는 것이다. 관리형 분류, 클라이언트 특성,
그리고 실제 요청 패턴 중 둘 이상이 일치할 때만 사용자 경험에 영향을 줄 수 있는 액션을
적용했다. 이 구조는 한 신호가 틀렸을 때 전체 정책이 잘못되는 위험을 줄여 준다.

## 왜 JavaScript Challenge였나

차단은 명확하지만 되돌리기 어렵다. 반면 JavaScript Challenge는 요청이 콘텐츠에 도달하기
전에 브라우저 동작을 검증한다. 일반적인 브라우저는 짧은 검증을 통과해 계속 이용할 수
있지만, 단순 HTTP 클라이언트나 일부 headless 자동화는 여기에서 멈춘다.

이 선택에는 두 가지 이유가 있었다.

- **글로벌 사용자 보호:** 특정 국가·통신사·IP 대역을 일괄 차단하지 않아 실제 사용자
  유입을 보존할 수 있다.
- **안전한 학습 루프:** Challenge는 발급, 통과, 유효 쿠키 확인, 실패 같은 결과를 남긴다.
  따라서 규칙이 예상한 대상을 맞히는지 다음 조정 전에 확인할 수 있다.

처음부터 모든 자동화에 Challenge를 걸지 않았다. Bot Manager에서 보이는 규칙별 성격을
먼저 로그로 확인했다. 어떤 분류는 합법적인 크롤러나 프레임워크 트래픽도 포함할 수 있으므로
계속 관찰만 했고, 다른 분류와 비브라우저 지문이 함께 나타난 범위만 Challenge로 전환했다.

## JA4 지문은 정밀하지만, 단독 규칙으로 쓰지 않았다

JA4는 TLS ClientHello 특성을 바탕으로 클라이언트 행동을 구분하는 데 도움이 되는 지문이다.
사용자 에이전트는 쉽게 바꿀 수 있지만 TLS 스택의 특징까지 같은 방식으로 흉내 내기는 더
어렵기 때문에, 분산 프록시와 자동화 트래픽을 관찰하는 보조 축으로 유용하다.

하지만 지문 자체가 사람과 봇을 완벽히 나누지는 않는다. 잘못 고른 넓은 지문은 일반
브라우저를 함께 묶을 수 있다. 그래서 다음 안전장치를 뒀다.

- 로그에서 충분히 반복되고, 비브라우저 동작과 함께 나타나는 지문만 후보로 삼는다.
- 정상 사용자가 많은 사용자군에서 같은 지문이 보이면 후보에서 제외한다.
- 첫 액션은 영구 차단이 아니라 JS Challenge로 시작한다.
- 변경 후에는 Challenge 결과뿐 아니라 정상 사용자 응답률도 같은 시간대에 비교한다.

WAF가 “완벽하게 봇을 알아내는 도구”라고 가정하지 않는 것이 중요하다. WAF는 신호를
결합해 위험을 낮추는 계층이고, 정책은 관측 결과에 따라 계속 좁히거나 되돌릴 수 있어야 한다.

## Challenge solve rate를 정책의 품질 지표로 삼았다

참조 글에서 가장 실용적이었던 힌트는 solve rate를 단순한 보안 수치가 아니라 **오탐 감지
지표**로 쓰는 방식이었다. Azure Front Door WAF의 JS Challenge 관련 지표도 같은 관점으로
읽었다.

- `Issued`: 새로운 Challenge가 발급된 요청
- `Passed`: 클라이언트가 계산을 완료해 응답한 요청
- `Valid`: 이전에 발급된 유효 쿠키를 제시한 요청
- `Blocked`: Challenge를 완료하지 못한 요청

`Issued`만 늘어도 성공으로 보지 않았다. `Passed`와 `Valid`의 비율, 콘텐츠 응답으로
이어지는 흐름, 그리고 정상 사용자군의 4xx 비율을 함께 확인했다. 통과율이 예상보다 높거나
특정 사용자군의 오류율이 오르면, 규칙 조건을 더 좁히거나 로그 모드로 되돌리는 것이 맞다.

반대로 표적 트래픽이 Challenge에서 거의 멈추고 정상 사용자 지표가 안정적이라면, 그 규칙은
적어도 현재 관측 범위에서는 좋은 분리 기준으로 볼 수 있다. 이번에도 의심 트래픽은 콘텐츠
요청 대신 Challenge로 전환됐고, 정상 사용자 흐름에는 의미 있는 악화가 나타나지 않았다.

## WAF 운영에서 남은 원칙

이번 대응을 거치며 WAF는 한 번의 “완성된 차단 정책”이 아니라 지속적으로 조정하는 운영
시스템이라는 점을 다시 확인했다.

- **서버 로그를 소스 오브 트루스로 둔다.** 클라이언트 분석 지표는 봇 트래픽을 충분히
  설명하지 못할 수 있다.
- **규칙마다 이유와 되돌릴 기준을 남긴다.** 무엇을 막는지, 어떤 지표가 나빠지면 롤백할지
  정책과 함께 기록한다.
- **광범위한 block은 최후의 수단으로 둔다.** 사람이 섞일 가능성이 있으면 먼저 좁은
  Challenge와 관찰 모드를 사용한다.
- **예외는 후순위가 아니다.** 검증된 크롤러와 운영 필수 트래픽을 먼저 정의하지 않으면
  좋은 봇과 정상 기능이 쉽게 피해를 본다.
- **방어 기능의 비용도 측정한다.** Challenge 자체가 성능이나 전환 흐름에 주는 영향까지
  관측해야 한다.

## 마치며

봇 공격 대응은 “더 많이 막는” 문제가 아니라 “무엇을 확신할 수 있는지”를 좁혀 가는
문제였다. GeekNews에서 읽은 사례는 분석 도구 밖의 트래픽, 분산 프록시의 한계, 그리고
Challenge solve rate의 의미를 구체적으로 생각하게 해 준 좋은 출발점이었다.

이번 대응에서는 애플리케이션이 만든 잡음을 먼저 제거한 뒤, Azure WAF의 Bot Manager,
JA4/TLS 지문, 검증된 크롤러 예외, JavaScript Challenge를 조합했다. 그 결과 넓은 차단 없이
자동화 트래픽을 콘텐츠 경로 앞에서 걸러내고, 정상 사용자 지표를 보며 규칙을 검증할 수
있었다. 다음 변경도 같은 원칙으로 시작할 생각이다. 먼저 관측하고, 좁게 적용하고, 결과를
보고 다시 조정한다.
